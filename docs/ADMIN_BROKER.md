# 管理员与经纪人后台

## 入口

- `/login`：共用账号登录；已开通管理员 / 经纪人登录后分别进入对应工作台。
- `/admin`：全站运营总览。
- `/admin/users`：用户资料与经纪人开通、停用、细分权限。
- `/admin/domains`：全站域名与状态管理。
- `/admin/reports`：全站历史分析报告。
- `/admin/orders`：委托受理、订单分配、重新分配、状态管理。
- `/admin/audit`：只读操作日志。
- `/broker`：获授权经纪人的订单与权限概览。
- `/orders`：普通用户提交出售 / 收购委托、查看自己的进度。

## 使用流程

1. 首位管理员由项目所有者指定并通过可信数据库管理连接初始化；不提供公开自助管理员注册。
2. 经纪人先正常注册，管理员在“用户与经纪人授权”搜索邮箱，勾选“开通经纪人后台”，选择接单、推进状态、添加跟进权限并保存。
3. 客户提交委托，或管理员为已有用户创建委托。订单初始为待分配。
4. 管理员选择已启用且有接单权限的经纪人，将状态设为待接单。
5. 经纪人接受 / 拒绝委托；接受后可依次开始跟进、标记完成，并添加内部跟进记录。
6. 停用经纪人后，其后续数据库访问立即受限；未完成订单保留，由管理员重新分配。

金额为 USD 需求字段，订单完成不执行付款、佣金结算或域名转移。内部跟进只对管理员及当前获授权的负责经纪人可见。

## 权限实现

- `staff_access` 单独存储受管理的权限，不使用用户可编辑的 metadata 或 profiles.plan 作为管理员依据。
- 管理员仅能通过后台授予 broker 身份，不能使用该表单创建、修改或撤销 admin 身份。
- 页面、Server Actions、数据库 RLS 和订单状态触发器共同校验权限；隐藏按钮不是权限边界。
- broker 不能修改委托人、域名、预算、联系邮箱、分配对象等字段，也不能直接跳转到任意订单状态。
- 更新使用订单 version 防止旧表单覆盖新状态。授权变更、订单变更、内部跟进和用户 / 域名修改自动写入只读日志。
- 提权检查和审计触发器放在非公开的 `app_private` schema，并撤销默认执行授权；应用不需要 service-role key。
- 新表仅授予必需的 SELECT / INSERT / UPDATE；匿名角色无表访问权限。

## 数据库部署

`supabase/sql/admin-broker.sql` 是新增结构的可审阅 SQL，依赖既有 profiles、domains、domain_analysis。目标项目已通过 Supabase MCP `apply_migration` 应用 `admin_broker_workspaces`；不要重复执行。

管理员初始化是独立的数据操作：根据已确认的 Auth 用户补齐 profile，再插入唯一的 staff_access admin 记录。生产账号邮箱和用户 ID 不写入公开源码。

## 配置与运行

登录通过本站 `/api/auth/login` 写入服务端会话 Cookie，然后执行完整页面跳转，避免浏览器 Cookie 与客户端路由缓存的时序问题。接口拒绝跨站请求，连接失败有明确提示并设有超时。

本地 `npm run dev` / `npm start` 使用启动脚本，在 macOS 上只读检测现有系统 HTTPS 代理；支持环境代理的 Node（建议 Node 24）会自动使用它，解决浏览器可访问 Supabase 但 Node 直连被重置的问题。不会改动系统设置或关闭 TLS 校验；线上没有配置代理时保持直连。

复制 `.env.example` 到 `.env.local`，填写 Supabase URL 和 publishable key。`OPENAI_API_KEY` 仅 AI 分析需要，后台管理不依赖它；OpenAI 客户端改为按请求初始化。

旧项目 Supabase 检查器仍有注册触发器公开执行授权、密码保护未开启等历史提示，本次新建私有权限函数没有新增此类提示。不要为解决后台访问错误关闭 RLS。
